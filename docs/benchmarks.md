# Benchmarks: what is measured, how to reproduce it

## The data

The maps and scenarios are the standard MAPF benchmark of Stern et al. (SoCS
2019), hosted with Sturtevant's grid-pathfinding benchmarks at movingai.com.
Nothing is generated by us and nothing is committed to this repository.

```
python3 tools/fetch_benchmarks.py --list      # URLs, sizes, hashes
python3 tools/fetch_benchmarks.py --all       # ~19 MB, into data/
python3 tools/fetch_benchmarks.py --verify    # re-check the SHA-256s
python3 tools/fetch_benchmarks.py --describe  # map dimensions, read from disk
```

| archive | size | SHA-256 |
|---|---|---|
| `mapf-map.zip` | 73.4 KB | `9da2e4c5ce03aa4e063b3a283ce874590b36cc4f31a297fe7ecb00d105abf288` |
| `mapf-scen-random.zip` | 7.9 MB | `20b7838f7a51f13e90a63ee138e9435fb4e41b0381becbc7313b7d3a7d859276` |
| `mapf-scen-even.zip` | 9.9 MB | `249896aaf15ef2d9beb378f954f0b7ca17189c6dec1b76a78965bbdbe714ad75` |

Both scenario sets resolve and are used: `random` (start/goal pairs drawn
uniformly, 25 files per map) is what the sweep runs on, and `even` (pairs
stratified over path-length buckets) is fetched and readable by the same parser
via `--scen-kind even`.

An instance with *k* agents is the **first k lines** of a scenario file. That is
the convention the whole literature uses, and it is the only reason numbers from
different implementations can be compared at all.

## The lower bound, and the trap in the .scen files

The last column of a `.scen` line is the **8-connected octile** optimal distance
(diagonal moves allowed, cost sqrt(2)), inherited from the grid-pathfinding
benchmark. MAPF is solved 4-connected. A 4-connected path is a legal 8-connected
path of the same cost, so the octile value is a valid but **loose** lower bound:
measured on `random-32-32-20` scenario 1, it is strictly below the true
4-connected distance for the large majority of pairs
(`tests/test_benchmark_data.py` asserts both the bound and the looseness).

So the ratios in the tables are measured against the **sum of true 4-connected
single-agent distances**, computed by backward Dijkstra. That is a genuine lower
bound on the optimal sum-of-costs (each agent must travel at least that far, and
other agents can only make it worse), and it is tight on open maps. A ratio of
1.000 means provably optimal.

The octile column is carried alongside in the CSV for reference.

## Running the sweep

```
python3 benchmarks/run.py --quick        # smoke test, a few minutes
python3 benchmarks/run.py                # the full sweep
python3 benchmarks/run.py --figures-only # re-render charts from results.csv
python3 benchmarks/make_figures.py --all # animations and diagrams
```

Configuration is `config/benchmark_default.json`: time budget, scenario ids,
algorithm list, and the agent counts per map.

## How to read the numbers honestly

* **One machine, CPython.** All timings come from a single CPU-only laptop-class
  machine running the pure-Python implementation in this repository. A tuned C++
  MAPF solver is far faster. The *shape* of the curves -- which algorithm
  survives to which agent count, what each improvement is worth -- is the
  comparable part; the absolute seconds are not.
* **Runtime includes the heuristic.** Each run builds its own true-distance
  tables, so no algorithm benefits from a previous run's cache.
* **Failures are not averaged in.** Runtime statistics use solved runs only:
  counting a 20 s timeout as "took 20 s" flatters a slow algorithm.
* **Truncated curves.** An algorithm that solves none of the instances at some
  agent count is not run at higher counts on that map. Those points appear in
  the CSV as `skipped` and are excluded from every average, so a line that stops
  early means "it had already failed everything", not "it succeeded".
* **Every returned plan is re-validated** from the paths alone -- endpoints,
  single-step moves, vertex conflicts and swap conflicts -- by code that does
  not share anything with the solvers. A plan that fails validation is recorded
  as `invalid`, and none were.

## Output

`benchmarks/output/results.csv` has one row per run:

```
map,scenario,agents,algorithm,status,runtime_s,sum_of_costs,makespan,
lower_bound,octile_lower_bound,ratio_to_lb,high_level_expanded,
low_level_expanded,w
```

`benchmarks/output/tables.md` is the rendered version of the tables in the
README.
